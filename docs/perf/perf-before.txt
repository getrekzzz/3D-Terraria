# Lag-spike baseline (W0, before any P1b lag fix)

Measured with the P1b-05 instrumentation (spike log, timer scopes, game/Testing/Scripts/perf.cmds) on top of the W0
prep commits (dfaad3b); no gameplay or rendering behaviour differs from that parent. P1b-06..16 compare against the
numbers below by running the same commands on the same kind of machine.

## Rendering run (the baseline)
Command (Xvfb + lavapipe, 2026-10-01, 4-core Xeon @ 2.1 GHz, load average ~4 from another lane building in parallel):
  xvfb-run -a -s "-screen 0 1600x900x24" env VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json \
    godot --path . --rendering-driver vulkan --audio-driver Dummy -- --world=perf --size=small --new --player=perf \
    --fresh-player --view=6 --graphics=medium --smoke=res://game/Testing/Scripts/perf.cmds
Result: SMOKE PASS, ~26 minutes wall time for 686 frames.

How to read it:
* lavapipe draws a frame in ~1.5 s, so physics runs its 8-step catch-up every frame (8 ticks per frame) and the
  frame.delta line (Godot's clamped process delta) reads 133 ms. FrameProbe therefore measures the main thread's own
  work (from the end of the last draw to the end of process): "frames (main thread, draw excluded)". These are CPU-side
  hitches inflated by the software rasteriser sharing the 4 cores; compare only with other lavapipe runs.
* The ring keeps the last 64 spikes; `perf spikes 10` lists the tail of the run (water, magic, creatures). The
  per-timer max/avg/calls in `perf report` cover the whole run (travel, save, autosave, torches, water, magic,
  creatures).
* A first attempt that measured whole frames (draw included) had every one of its 699 frames over 100 ms
  (p50 1.5 s, worst 18 s): useless for hitches, hence the main-thread basis on software renderers.
